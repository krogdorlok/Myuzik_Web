# M3: Live Listen over WebSockets

- Built: an AudioWorklet does the downmix, windowed-sinc low-pass, fractional 16 kHz resample and Int16 conversion, posting 0.96 s frames. On top of that sit the `LiveSocket` class, the `useLiveListen` hook (EMA smoothing, stop/start race guards), a transcript timeline with *Jump to live*, and the FastAPI `/ws/listen`, which has single-use tickets, an Origin check, session resume and per-user caps, an idle timeout and inference throttling.
- Measured (`docs/metrics/live.json`): frame round-trip p50/p95, about 31.8 kB/s upstream against 192 kB/s for raw capture, and recovery after a forced disconnect.
- Trade-off 1: under backpressure, frames are dropped rather than queued (`bufferedAmount` above 4 frames). A stale frame from 5 s ago is worse than no frame: it delays every later prediction, and the genre display would lag the music.
- Trade-off 2: a one-time ticket rather than putting the JWT in the WebSocket URL. URLs end up in proxy logs and browser history, and Vercel route handlers can't proxy WebSockets, so the socket has to go straight to FastAPI. A ticket that expires in 30 s and works once leaks nothing of lasting value.
- Defend: the AudioWorklet runs on the real-time audio thread, while ScriptProcessorNode ran on the main thread and glitched whenever React rendered. The filter cuts at 7.2 kHz with a transition of about 2.5 kHz, so anything that would fold into VGGish's 125 Hz–7.5 kHz mel range lands in the stopband. Also, one 15,360-sample chunk yields zero VGGish embeddings, so the server buffers 2–3 chunks before predicting.
